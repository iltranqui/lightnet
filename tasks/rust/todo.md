## P6 FP16 (C++ reference: cuda_f32_to_f16/cuda_f16_to_f32 in blas_kernels.cu, cuDNN half conv path; cuda-device has `f16.rs`, `bf16.rs`, `f16x2.rs`)
Design decision first: trait `F32TensorOpsBackend` is f32-only. Pick (a) new `F16TensorOpsBackend` trait / mixed-precision mode where weights+activations stored as f16 with f32 accumulate and f32 master weights, or (b) internal fp16 compute inside f32 API (convert at GEMM boundary). Recommend (a) for inference storage savings; write the decision here before coding.
- [x] Decide API (a vs b), document in plan + here -> DECISION (2026-10-01), SCOPE = INFERENCE ONLY (training stays f32, mixed-precision training stays open in P8):
  - Chosen: (a) f16 STORAGE + f32 accumulate, but as an additive, opt-in surface, not a rewrite of the f32 trait: new `darknet_cuda::F16TensorOpsBackend: F32TensorOpsBackend` (assoc `TensorF16`, only the ops an inference graph needs: f32->f16 weight prep, conv2d+bias+activation, maxpool, route, upsample, upload/download) implemented by `OxideBackend` over a new `OxideTensorF16` (u16 bit patterns, own buffer pool). `GpuExecutableNetwork::forward_compact_f16` (method-level `where B: F16TensorOpsBackend`) is the f16 twin of `forward_compact`; the f32 trait, runtime state, training and CPU fallback are untouched.
  - Why not (b) alone: it would keep f32 activations in memory (no storage/bandwidth win, which is the point of fp16 for inference) and pay a convert pass per GEMM operand.
